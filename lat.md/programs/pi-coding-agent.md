# Pi coding agent

This file covers how Pi is packaged, wrapped, configured, and extended in this repo. The configuration lives at `home/.pi/`.

The former Home Manager module (`nix/home/common/programs/pi-coding-agent/`) and vendored `pi-acp` adapter are removed. Current Home Manager generations claim no Pi files.

## Mise-managed configuration

`home/.pi/` is the sole owner of Pi configuration, wired through `config/mise/config.toml`.

`mise run up` (alias `dot`) runs named update phases sequentially through `mise/scripts/update-machine` and stops on the first failure. The updater sends each phase's combined stdout and stderr directly to the terminal so child tools retain native TTY behavior, prints each exit code, and reports the failed phase.

`agent/` holds the managed subset of `~/.pi/agent` applied through `[dotfiles]` symlink and `symlink-each` entries; `bin/` holds the `pi`, `p`, and `work-tickets` wrappers linked into `~/.local/bin`. The extension, skill, prompt, and agent mappings exclude every `_*` path component, so disabled entries remain beside active entries with an underscore prefix and disappear from the runtime directories on the next apply. The hk shell and TypeScript linters use matching exclusions, while repository-wide safety checks still inspect those files. During the path-only move, `mise/scripts/lint-pi-files` skips only staged destination additions whose old source is staged for deletion and whose index and working-tree blobs match the old source; after the move lands and the old path leaves `HEAD`, the helper lints every changed Pi TypeScript and JavaScript file normally. `mise/tests/pi-resources.test.sh` applies the real mappings to a temporary home, checks active and disabled resources, loads every active extension entry point through the installed Pi CLI, and verifies that every mapped skill and prompt is discoverable. `mise/scripts/update-pi` implements `update:pi`: it installs the sha256-pinned Plannotator helper into `~/.pi/agent/bin`, extracts the nicknisi/sessions plugin in an isolated home, cleans redundant extension dependencies, upgrades the mise-managed Pi package, and runs `pi update` plus `pi update --extensions`. `mise run update:pi -- --dry-run` previews helper-bin changes, cleanup targets, and Pi update commands without modifying files. This task does not apply the `[dotfiles]` mappings; `update:dotfiles` handles those separately. The former `pinvim` and `pview` wrappers remain under `disabled/` because `~/.local/bin` uses a separate unfiltered mapping; active profile resolution runs through `scripts/resolve-profile.mjs` from `bin/pi`.

`update:pi` prints persistent start and success lines for each step, reports the failed step and exact exit code, and stops before later steps. The step wrapper leaves child streams untouched. Only the nested `mise upgrade` uses `--raw`: mise 2026.9.9's [clx 3.0.2 renderer](https://github.com/jdx/clx/blob/v3.0.2/src/progress/render.rs) clears the visible screen on resize or when its progress region fills the viewport; mise also removes completed progress rows. Raw mode avoids those redraws while retaining native TTY color and child output. Isolated fake-tool PTY tests reproduced resize clearing with ordinary mise output and no clearing with `--raw`; no live package upgrade was needed. Pi 0.87.0 also checks npm versions silently and batches only outdated packages, so fewer per-package messages do not mean extension updates were skipped.

`lat` resolves from mise's `npm:lat.md` tool. Mise links `~/.pi/agent/bin/lat` to its stable shim because Pi's lat extension tools launch through that agent-local path; no lat override points back to Devenv.

The managed `agent/extensions/lat.ts` passes arguments directly to `execFileSync`, captures child stderr, and reports command failures through tool results. Its lifecycle hooks stay dormant unless the working tree contains `lat.md/`. LAT diagnostics must never write directly into Pi's alternate-screen TUI because they can overwrite the input editor.

`config/mise/config.toml` prefers canonical mise registry aliases for user-facing tools and keeps backend-qualified names only when the registry has no alias or a specific package source is required. It installs `plannotator-tui` through the Cargo backend for manual use. The `_plannotator-tui` skill is disabled until the TUI can open in the current Pi tmux window and exchange feedback with Pi in both directions; the browser-based `@plannotator/pi-extension` remains the active review integration.

## Package source and wrapper

Pi comes from the mise tool `npm:@earendil-works/pi-coding-agent`; the managed wrapper at `home/.pi/bin/pi`, linked as `~/.local/bin/pi`, resolves the CLI through mise.

The sibling `p` script executes this wrapper directly. `ftm`'s canonical worktree and generic agent windows explicitly launch `"$HOME/.local/bin/pi"`, retaining `-c` or `--session <uuid>`; they do not rely on bare `pi` resolution through `mise exec`. The wrapper itself loads the project environment through mise and enables bridge ingress. This affects newly created agent windows, not already-running processes.

The wrapper resolves the real binary by absolute path (`mise which pi`) and passes it to `mise x` explicitly. Relying on `mise x ... -- pi` PATH lookup broke: mise splices tool paths into the existing PATH block instead of prepending, so the wrapper's own `~/.local/bin` export shadowed the real binary and the wrapper exec'd itself in an infinite loop. A realpath self-check fails closed with exit 127 if resolution ever points back at the wrapper.

The wrapper sets `PI_STATE_DIR`, creates socket and manifest state directories, exports `PI_BRIDGE_LEGACY_SOCKET=1` so the generic bridge owns Pi-to-Pi `/tell` ingress, prepends `~/.pi/agent/bin`, `~/.local/bin`, mise shims, and `/opt/homebrew/bin` to `PATH` for launch contexts without shell init, and resolves `mise` plus `fnox` before launch. Its empty-array expansions remain compatible with macOS Bash 3.2 under `set -u`, because the shebang selects Bash before the wrapper can prepend Homebrew to `PATH`. It exports only non-secret `LAT_LLM_*` provider metadata; fnox injects `LAT_LLM_KEY` from the Synthetic alias in `config/fnox/config.toml`. The final handoff is `fnox exec --replace -- mise x npm:@earendil-works/pi-coding-agent -- pi`, so non-shell Pi launches receive secrets without sourcing rendered files. `poppler-utils` stays in nix `nix/home/common/packages.nix` on megabookpro (mise's `brew:poppler` covers workbookpro).

The `git-worktrees` skill checks `wt --version` before managing worktrees. When available, it documents the v2 contract: `wt NAME` (full setup + canonical session presentation, like `wt open`; `-t cd` is the parent-shell-cd escape hatch), `-t cd|w|s` presentation targets, `wt open`, bare `wt repair` for the containing checkout, `wt path`, `wt list --json`, and `wt prune` with refusal/partial-recovery semantics; agents are steered to `wt ensure NAME --json` plus `wt path` because agent bash calls cannot cd the parent shell. Raw `git worktree`, manual `GIT_WORKTREE`, copy loops, manual tmux layouts, and `wt switch` for navigation stay forbidden (`wt switch` now passes through to the raw upstream backend — no parent-shell cd, no tmux). The `merge-worktree` prompt's cleanup step uses `wt prune` instead of forced raw removal. It preserves prior manual instructions in `skills/git-worktrees/references/legacy-git-worktrees.md` and uses that reference unchanged only when `wt` is unavailable.

Pi Dictate is a repo-managed local extension at `agent/extensions/pi-dictate.ts`, forked from `github.com/amosblomqvist/pi-dictate` commit `46a8609`; the upstream git package entry is removed to prevent duplicate shortcuts and lifecycle handlers. Alt+M starts/stops and Alt+N cancels. The local `pi-bash-live-view` widget patch (kept at `home/.pi/patches/pi-bash-live-view/widget.ts`) makes live PTY panes fit rendered lines by display cell width, preserving ANSI escape sequences while trimming wide glyphs, combining marks, zero-width joiners, and variation selectors before padding to the terminal width. This avoided the one-cell overflow crash seen when live output contains wide glyphs or ANSI-colored truncation edges. The `bin/pi` wrapper no longer copies it over the installed widget at launch; the file remains only as reference in case the upstream regression returns.

The `pi-acp` ACP adapter (vendored package, wrapper, `~/.local/bin/pi-acp` link, and pi-update build step) is deleted entirely, not migrated.

## Session and routing extensions

The `/answer` extension can be invoked by its slash command, Ctrl+. shortcut, or the internal `trigger:answer` event.

`notify.ts` passes `--presence-routing` to `bin/ntfy`, making Pi notifications the sole automatic opt-in for Telegram delivery when Hammerspoon reports `remote_only` (display asleep, locked, logged out, or idle). Other `ntfy` callers and all current notiwatchd rules require explicit phone or Telegram routing. Completion now follows `agent_settled`, not low-level `agent_end`, so automatic retries, compaction continuations, and queued follow-ups resolve before one delayed notification is scheduled. New input cancels that pending notification. The final assistant result controls the outcome: successful turns send a bounded plain-text excerpt, a final normalized `Connection error.` sends nothing, and other errors send useful failure text. Structured prompts notify immediately and suppress a duplicate settled question alert. The stable inbound Telegram contract is the exact prefix `📱 **Telegram message:**\n`, followed by the unmodified message body; ingress implementations must preserve that marker. `notify.ts` checks `event.text.startsWith()` against the prefix, suppresses structured and settled notifications for that complete run across retries, then clears the run marker. Ordinary local input never suppresses notifications.

Pi fullscreen transcript search (`tui.altScreen.search`) keeps Ctrl+Shift+F; the local `files.ts` Finder reveal action moved to Ctrl+Shift+E so no extension shadows that core binding. `files.ts` still owns Ctrl+Shift+O and Ctrl+Shift+R, and `preview.ts` owns Ctrl+Shift+P.

Turned-off extensions (`_execute-command.ts`, `_pinvim.ts`, and `_nvim-review.ts`) and the `_pinvim-kitty-test` skill remain beside active entries with underscore prefixes. The mise exclusions keep them out of Pi's runtime directories. Neovim-side pinvim source remains in place, but ordinary Pi no longer loads its socket polling, editor-service RPC, footer updates, or review command.

`multi-sub.ts` owns `/subs`, `/pool`, and multi-sub pool or chain failover. When a rate limit rotates the pool while Pi is still processing the failed turn, retrying the same prompt must use `deliverAs: "steer"` or the core session rejects it as already processing.

As of pi-coding-agent 0.83.x, subscription clones are registered as **native pi-ai `Provider` objects**. The extension loader only aliases four pi-ai specifiers for extensions (`@earendil-works/pi-ai` → `dist/compat.js`, `/compat`, `/oauth` (types-only), `/providers/all`); any other subpath such as `auth/oauth/load` fails to resolve. `registerSub` therefore looks up the builtin provider via `builtinProviders()` from `@earendil-works/pi-ai/providers/all` and calls `pi.registerProvider({...base, id, name, auth: { oauth: base.auth.oauth }, getModels, refreshModels: undefined })`. Clones are OAuth-only (no api-key env fallback, so an env key doesn't make every clone look configured), credentials are stored per provider id so each clone logs in separately, and cloned models carry `provider: <clone name>`. `registerSub`/`cloneModels` are sync; activate-time registration clones the static builtin catalog, and `session_start` re-registers with registry-composed models. Preset entries must use the same canonical model ids exposed by the registry and scope lists, for example `gpt-5.6-sol` rather than `gpt-sol-5.6`.

Earlier, as of pi-coding-agent 0.80.x (pi-ai 0.80.8), the extension was migrated to the then-new SDK APIs:

- **OAuth login flows removed**: pi-ai 0.80.8 removed `anthropicOAuthProvider`, `loginAnthropic`, `refreshAnthropicToken`, and all other runtime OAuth helpers from `@earendil-works/pi-ai/oauth`. `/subs login` points users at pi's built-in `/login`; `/subs logout` works best-effort through the private `ModelRuntime.logout()` behind `ModelRegistry`.
- **Google providers dropped**: `google-gemini-cli` and `google-antigravity` are no longer supported (pi-ai 0.80 dropped those OAuth providers entirely). `PROVIDER_TEMPLATES` now only includes `anthropic`, `openai-codex`, and `github-copilot`, each with just a `displayName` field.
- **`getModels` removed**: pi-ai 0.80 removed the standalone `getModels(provider)` export. All call sites now use `ctx.modelRegistry.getAll().filter((m) => m.provider === provider)` for built-in model lookups.
- **`ModelRegistry.authStorage` removed**: the old `authStorage` property on `ModelRegistry` is gone. A `getAuthStorage(registry)` adapter mimics the old sync interface for the extension and `PoolManager`: `hasAuth` via `getProviderAuthStatus(provider).configured`, `get` always returns `undefined` (no sync credential access), `logout` best-effort via the private `ModelRuntime.logout()`. `collectQuotaAccounts` is async and fills access tokens with `getApiKeyForProvider()`, so the codex quota checker still authenticates; `accountId`/`projectId`/`expires` metadata is no longer available (codex falls back to JWT claims).
- **Quota checker**: only `codexQuotaChecker` remains. Google Gemini and Antigravity quota checkers and all Google-specific helper functions/constants/types were removed (~650 lines).
- **`cloneModels` and `registerSub`**: accept `Model<Api>[]` and `ModelRegistry | undefined` params respectively. With `undefined` (activate time) the static builtin catalog is used.
- **Cross-extension auth sharing**: the scoped/named auth groups (sub entries, pools) are stored in `settings.json` under `multiSub` and cached in `_cachedSubs`. The extension exposes this via the `/subs` command surface and the `PoolManager` class.

The `/goal` extension persists one long-running goal in session custom entries, injects it before agent turns, tracks token and elapsed usage, supports pause/resume/clear, enforces optional token budgets, and exposes `get_goal`, `create_goal`, and `update_goal`. Completion requires evidence-based auditing before `update_goal { status: complete }`.

The `/handoff` extension replaces the disabled `_handoff` file-backed skill: it serializes branch and session-chain context, asks the selected model for a self-contained next-thread prompt, and writes the exact prompt to `~/.local/share/pi/handoffs/$(basename $PWD)/<timestamp>.md` before opening a new session with `parentSession`. Generation reads `ctx.thinkingLevel` at request time and uses `ctx.modelRegistry.streamSimple(...).result()` so registered providers, request-time authentication, and provider-neutral reasoning levels are honored. `off` maps to an undefined `reasoning` option; enabled levels, including `xhigh` and `max`, pass through unchanged. No separate thinking preference is cached by handoff. It uses `newSession({ withSession })` to leave the unsent prompt in Pi's replacement-session editor, where the user can invoke `app.editor.external` explicitly.

`agent-status.ts` publishes this pi's coarse activity state (`idle`/`working`/`asking`/`error`/`done`) to `$PI_STATE_DIR/status/pi-{session}-{window}.status` (line `state pid session`) from lifecycle events (`agent_start`, `agent_end`, `input`, `tool_call`/`tool_execution_end` for `ask_user_question`, `error`), modeled on fleet's hook approach. A turn that ends after an `error` event writes `error` (was `idle`), so pickers can flag it as needing attention. `agent_end` also applies a prose-question heuristic: when the turn's final assistant message text ends with `?` (after trailing markdown/quote/paren noise), it writes `asking` instead of `done`, so prose questions surface as waiting-on-user. Only interactive tmux pis publish (`ctx.hasUI` + `TMUX`); the file is removed on `session_shutdown` and readers must pid-validate to skip crash leftovers. `bin/ftm` reads these files for its picker status dots.

`resurrect-tag.ts` tags the surrounding tmux pane with the session UUID (pane option `@pi_session_id`) on `session_start` and clears it on `session_shutdown`. Both ftm snapshots and tmux-resurrect use the tag to restore the exact Pi conversation as `pi --session <uuid>`; no restore command invokes pinvim.

The `/tell` extension replaces the shell-script tell skill for Pi-to-Pi guidance. Bridge ownership uses owner tokens and socket inodes: manifests are written after a successful listen, heartbeats identify stale owners, and shutdown checks ownership before closing or removing registration. Stale reclaim requires an identified dead owner and a valid old heartbeat; a start timestamp alone, missing or invalid heartbeat evidence, and ping failure never authorize reclamation. Discovery merges manifests and sockets with tmux panes (including orphaned Pi processes), preserving stable candidate IDs, logical Pi session metadata, machine/session/window/pane metadata, cwd, pid, state, and reachability. Each tmux pane gets its own bridge socket, so adjacent Pi processes in one window remain independently reachable. It ignores ephemeral entries for selection. `tell_pi` and `/tell` support explicit `steer` or `follow_up` delivery while retaining `follow_up` as the busy-session default. `list_pi_sessions` and `/tell-sessions` expose local or remote discovery; `get_pi_last_message` and `/tell-last` retrieve the selected session's last assistant text. `bin/pi` enables the generic bridge directly; bridge has no pinvim heartbeat, peer scan, footer status, or Neovim protocol handling. Incoming tell messages are persisted as `tell-message` custom entries before delivery, surfaced near the editor through a temporary widget, and mirrored through the same best-effort `~/bin/ntfy` path retained from disabled pinvim.

Bridge serializes startup within each runtime and takes an exclusive `${socket}.claim` file across stale reclamation, binding, and manifest publication. Contenders retry without changing the socket or manifest. Claim release checks the acquired inode and owner; abandoned claims remain blocked for manual recovery and are not stolen using PID or age guesses. This coordinates upgraded startup paths, not legacy listeners or every heartbeat/shutdown mutation. A missing manifest can be restored with exclusive creation only while the listener's inode remains ours; an existing foreign registration is never overwritten by watchdog recovery. Displaced listeners are retired from message dispatch, and shutdown waits for pending startup work before releasing owned resources. Session startup resets shutdown/activity state and uses the current extension instance's latest Tidewave status; manifests use the active context's cwd.

Discovery waits for complete newline-delimited responses, handles split UTF-8 input, validates manifest and protocol shapes, and measures reachability by ping rather than treating a live PID or socket file as a working endpoint. Tell's local and remote response readers enforce absolute deadlines and 1 MiB byte limits, so a peer sending an endless partial line cannot hold discovery open. Local and remote tmux discovery use process executable names (`ps comm`) rather than command arguments, reconcile legacy records by PID, and deduplicate linked panes. Stale records cannot suppress a new process in the same pane; live ephemeral owners remain excluded. Current-instance detection uses the manifest PID and is recomputed when tmux correlation supplies a missing PID. Remote inventory retains registration identity separately from refreshed tmux display coordinates, so stable IDs survive window renames and pane moves. SSH and malformed remote-inventory failures are explicit errors, distinct from a successful empty inventory; both SSH entry points reject option-like destinations and place `--` before the machine argument.

Bridge and tell publish separate load-time identities (`version`, `loadedAt`, and `sourceHash`) as `bridge` and `tell` manifest fields. Tell emits `tell:runtime` on session startup; bridge validates the event and removes its subscription on shutdown. Ping replies add `runtime: { bridge, tell }`, PID, logical session metadata, and `idle`/`pending` snapshots. Compare those captured hashes with the managed files to verify loaded code. Updated symlinks, heartbeat freshness, and process start time alone do not establish which code a Pi process has loaded.

Reloads require a user-controlled safe boundary. In Pi 0.86.1, `sendUserMessage()` defaults to literal chat even when `deliverAs: "followUp"` is set. Opting into `expandPromptTemplates` dispatches extension commands immediately, before streaming queue handling; it does not queue a reload command. `ctx.reload()` exists only on command contexts. `waitForIdle()` covers ordinary agent continuations but does not provide an admission lock for input preflight, blocking UI prompts, or the TUI's separate compaction queue. Bridge therefore exposes no automatic reload endpoint. Do not send `/reload` as tell text, inject tmux keystrokes, or interrupt a task to refresh it. Existing instances need an ordinary user-initiated reload after work and queues drain, or a later session replacement. A process whose original Pi installation has been removed needs a separately planned graceful restart/resume; do not assume reload can repair its missing runtime dependencies.

`/tell` accepts `machine target message` as a remote form, for example `/tell megabookpro mega do something`. Remote routing first SSHes to the machine for JSON inventory from manifests, socket files, tmux panes, and descendant Pi processes. The sender applies the same ranking and selection rules locally, then uses a second SSH call to send to the selected socket's exact path. This supports shortened and explicit `PI_SOCKET` paths recorded in manifests and avoids first-glob guessing. Local machine prefixes such as `/tell workbookpro mega ...` are normalized back to local target routing. Remote tell payloads omit `fromSocket`; replies use the generated `/tell <origin-machine> <origin-session:window> ...` hint instead of socket ack.

Outside tmux, bridge uses a process-specific `pi-process-{pid}.sock` instead of a shared default socket. Bridge publishes its socket through `PI_SOCKET` with `PI_SOCKET_OWNER_PID`; bridge and tell ignore that marked path in a child process, while an unmarked explicit override remains supported. The process-specific path uses the same shortening function as tmux paths.

Bridge socket paths follow `${PI_STATE_DIR}/sockets/pi-{session}-{window}-{paneId}.sock`; legacy `${PI_STATE_DIR}/sockets/pi-{session}-{window}.sock` listeners remain discoverable while already-running Pis drain. The stable tmux `pane_id` suffix prevents two Pi processes in one window from contending for one socket and avoids collisions when `pane_index` changes after pane swaps or removals. macOS limits `sun_path` to 104 bytes and `net.Server.listen()` throws `EINVAL` past it, so `agent/extensions/bridge.ts` and `agent/extensions/tell.ts` share one deterministic shortening scheme: when the full path would exceed 103 bytes, truncate the `{session}-{window}-{paneId}` name by whole Unicode code points within the UTF-8 byte budget and append `-` plus the first 8 hex chars of its sha256. A socket directory that cannot fit even the hashed name fails explicitly. Hammerspoon does not reconstruct pane-qualified paths; it resolves them from manifests, while its path builder remains only for legacy window-level sockets. Bridge manifests keep stable `pane` socket identity separate from logical `sessionId` and mutable `sessionName`; they also store current `windowIndex`, `paneIndex`, `ephemeral`, `tidewaveConnected`, and optional `tidewaveEndpoint` fields. Heartbeats refresh mutable indices and logical names, so discovery and Hammerspoon can route by the human tmux address even when the basename is hashed. Headless and spawned Pi processes have no tmux metadata; their heartbeats skip tmux index refresh instead of treating two absent pane IDs as a match and dereferencing null. Tmux identity detection in bridge.ts and tell.ts passes `-t "$TMUX_PANE"` to `tmux display-message`; without it tmux reports the client's active window. bridge.ts resolves all tmux fields (`session_name`, `window_name`, `window_index`, `pane_id`, `pane_index`) in one tab-separated `display-message` call rather than five, because detection runs at startup and on every heartbeat. `tidewaveConnected` requires two validated event inputs: exactly one enabled `tidewave` server with `status: connected` in the stock adapter's `pi-mcp-adapter/status/v1` snapshot, and an endpoint from ACP's `pidewave:endpoint:v1` event. ACP publishes only the literal URL of its active runtime registration, confirmed through the adapter's runtime-snapshot API; see [[lat.md/programs/pi-coding-agent#Pi coding agent#Runtime settings#Tidewave endpoint publication]]. Tool availability, cached metadata, config mirroring, and HTTP probes never authorize the shortcut. The endpoint must have a canonical HTTP(S) origin on `localhost` or `127.0.0.1`, an effective port in `1..65535` other than the IDE port 9832, and pathname `/tidewave/mcp`, with no credentials, query, or fragment. Bridge publishes the validated pair as `tidewaveEndpoint` and updates it when either event changes. Factory-local state accepts either event order before or after `session_start`; publication needs no prompt once both inputs exist. Shutdown revokes authorization before draining the listener and removes both subscriptions. A replacement runtime starts unauthorized until it receives its own events. Missing or duplicate Tidewave entries, missing or unsafe endpoints, malformed events, and unsupported versions revoke authorization and remove endpoint identity. The manifest shape and pane/PID/cwd ownership checks stay unchanged. This source is mise-owned under `home/.pi/agent/extensions/`, with no Nix twin to sync. The template script `config/mise/tmpls/elixir/scripts/worktree-for-port.sh` is the runtime inverse of `phx-port.sh`: given a Phoenix dev port (or none, to detect the caller's), it finds the `phx.server` beam listening on that port and emits JSON `{port,pid,root,worktree,session,pgport,phxPort}`, where `session` is the live tmux session whose `session_path` is the worktree root (the ftm/wt worktree name, not the `.envrc` `SNAME`). `root` is the actual filesystem path and may end in a branch-only directory such as `sm-spp-enable-auth`; `worktree` and `session` are logical Worktrunk/tmux identifiers such as `provider_portal-sm-spp-enable-auth`. The prefix difference is intentional. Toolbar routing takes its origin from the reported connection endpoint and uses the listening `port` plus `root` as a worktree cross-check; it never falls back to an inferred port. The optional ACP binding filename uses the root basename.

Cmd+Shift+C starts [[lat.md/programs/hammerspoon#Tidewave inspector handoff|Tidewave browser inspection]] only for the actually focused, connected tmux Pi. Hammerspoon's event tap invokes one timeout-bounded helper to verify the focused Ghostty title, exact active tmux pane, fresh pane-qualified manifest, foreground Pi PID, and socket ownership. Ineligible presses pass through. Deferred execution and the final handoff revalidate the captured registration; HTTP liveness never substitutes for Pi's connection report.

Routing requires an existing Helium app page on the reported endpoint's exact origin and a live Phoenix listener in Pi's worktree. It never launches Helium, opens tabs, or navigates them. The unique saved CDP target prefix survives in-tab navigation; otherwise only a sole matching normal app page is accepted. `/tidewave` routes, missing pages, and ambiguous selection stop the handoff. Helium must own CDP port 9223 before tab discovery. After selecting the tab, the injected JavaScript checks the origin and waits for a visible, loaded page and enabled Inspect button. It clicks once only when inactive, then confirms the selected button and inspector panel.

Only successful Inspect activation updates `${PI_STATE_DIR}/tidewave/bindings/<worktree-slug>.json` with the reported canonical `appUrl` and CDP `targetPrefix`. ### Sentinel guardrail rules

Sentinel and the stop hook are disabled in managed source; their unchanged implementations remain as `_sentinel.ts` and `_stop-hook.ts` under `home/.pi/agent/extensions/`.

The mise `symlink-each` mapping excludes `_*` entries, so neither is selected for installation. Existing sessions may retain previously loaded extensions until reload or restart. No runtime cleanup or reload is implied by these source renames.

The following describes the retained Sentinel implementation, not a currently enforced policy. When explicitly loaded, Sentinel supplies Pi command guardrails, replacing the former JSON rule file. `extensions/sentinel-rules.json` is no longer installed or read. Debug logging is opt-in through `PI_SENTINEL_DEBUG_LOG` or `PI_SENTINEL_DEBUG`; it writes to a file instead of stdout/stderr so guardrail messages cannot corrupt the TUI editor. When enabled, startup logs 14 conceptual classifier rules instead of expanding every interactive command and preferred-tool entry into separate runtime rules.

The classifier rules are `hard-interactive`, `hard-vcs-editor`, `hard-managed-config-write`, `hard-nix-build-result`, `hard-destructive-system-rm`, `hard-secret-tools`, `hard-gatekeeper-secrets`, `confirm-security-sensitive-bash`, `confirm-remote-effects`, `confirm-package-install`, `confirm-history-destructive`, `confirm-tcc-reset`, `rewrite-preferred-tools`, and `rewrite-builtin-grep`.

The bundled tables still feed those classifiers for interactive jj, Docker, Kubernetes, Nix REPL, database shells, language REPLs, pagers, editors, and preferred-tool rewrites. Rewrites include `find` to `fd`, `grep` to `rg`, `rm`/`rmdir` to `trash`, and `python -m json.tool` to `jq`. Sentinel no longer rewrites `git` to `jj`.

Sentinel has three rule tiers: hard blocks cannot be overridden, confirm blocks can be retried after an explicit override, and rewrite blocks force a preferred tool or safer pattern. The `/sentinel on` and `/sentinel off` commands toggle all Sentinel guardrails for the current session; turning it off clears pending blocked and override state and prepends a red `` marker to the chat input editor until re-enabled. Confirm overrides are single-use, expire after 120s, and are tied to the exact command or write path; `override`, `bypass`, or `force` open UI confirmation when available, while `!override`, `!bypass`, `!force`, and `!!` grant immediately for the last blocked confirm rule.

Sentinel uses a shell-aware parser before rule matching. It strips quoted strings and heredocs, unwraps environment assignments, `sudo`, `command`, `env`, shell `-c` wrappers including `bash -c --`, command substitutions, absolute command paths, and simple `xargs` command forms. This keeps preferred-tool rewrites and safety confirms effective for wrapper forms such as `command grep`, `env grep`, `/bin/grep`, `sudo -n grep`, and `sh -c 'grep ...'`; it remains a UX guardrail, not an OS sandbox.

Specialized guards stay as code because they need context-specific parsing, filesystem checks, or side effects: VCS editor/message flows, managed or symlinked config writes, unsafe `nix build` output, destructive system-removal hard blocks, secret tools and gatekeeper scans before push, security-sensitive bash confirms, sensitive-path write confirms, session write/execute correlation, push/deploy/ssh confirmation, package install confirmation, investigation-only prompts, and pipe/redirect hang prevention. The managed-config guard blocks broad managed config prefixes and symlinks that resolve into `/nix/store/` or `~/.dotfiles/`, steering writes to the owning source path.

Security-sensitive bash confirms cover remote pipe execution through `curl` or `wget`, privilege escalation via `sudo` including absolute paths, persistence hooks, shell-config writes, and system binary installs. Sensitive-path write confirms use path-specific override keys so one approved `write` or `edit` cannot grant a later different path.

Session write/execute correlation records allowed `write`/`edit` targets and asks for override before executing a session-written script whose current contents contain risky patterns such as `curl | bash`, `eval`, recursive delete, `chmod 777`, `sudo`, or persistence hooks. Direct execution (`./script` or absolute path) and shell execution (`sh script`) both resolve against the current working directory before checking the session registry.

Investigation mode remains a guardrail outside the rule table. Prompts that start as imperative `investigate`, `inspect`, `audit`, or `check` block write-capable tool calls plus bash write workarounds unless the prompt includes implementation intent or the user grants the existing override flow.

The pipe/redirect guard blocks `bash` commands that pipe or redirect risky upstreams unless the tool call passes a `timeout` between 1 and 300 seconds. Database shell guards allow explicit noninteractive query forms such as `psql -c`, `mysql -e`, and `sqlite3 DB SQL` while still blocking interactive shells, and editor commands are treated as interactive even when passed file paths.

Package-install confirms cover Homebrew, global package installs, project dependency installs, and one-shot runners such as `npx` and `bunx`; installs under the managed Pi package source directory are allowed so local extension package work can run `npm install` without override. Push, deploy, SSH/SCP/remote-rsync, broad history-changing jj commands, and destructive Git history commands remain confirm-only so the agent cannot perform remote side effects or destructive history changes without explicit user approval.

The local `checkpoint.ts` extension is removed from the active profile; checkpoint and main-branch prompting come from the agent harness instead.

`claude-code-use.ts` is a local fork of `@benvargas/pi-claude-code-use` that renames extension tools on the wire instead of dropping them, omitting companion-package auto-loading for packages not used here.

That combination once let `dev:setup` write its completion marker without generating `.pi/`. Both outputs are built in memory, then written through temporary files and atomic moves. `preflight` uses mise's default `sh -o errexit -c`, because a custom `shell = "bash -c"` drops errexit; `dev:setup` sets `-euo pipefail` itself. Bootstrap failures now stop `mise run bootstrap`, `preflight`, `dev:setup`, and therefore `wt`/`ftm` setup.

The global `home/.pi/agent/mcp.json` sets `settings.allowInstall: false`. Otherwise the adapter's agent-callable `mcp({action: "install"})` persists URLs to project `.mcp.json` or the global config; an agent once wrote a numeric `mcpServers.tidewave` into a worktree's `.mcp.json`, which shadows ACP's runtime registration. User-typed `/mcp setup` and `/mcp enable|disable` can still write MCP configs.

The Elixir template's bootstrap tests live in `config/mise/tmpls/elixir/tests/bootstrap-pi.test.ts`, separate from its `scripts/` implementation. They run every case under `/bin/bash` and the `PATH` Bash. Run them from the repo root with `mise exec -- bun test ./config/mise/tmpls/elixir/tests/bootstrap-pi.test.ts`.

Accepted trade-off: runtime servers are proxy-only, and registration does not wake a deferred adapter. With warm metadata and no configured eager/keep-alive server, an MCP operation must initialize it; `/mcp reconnect tidewave` explicitly initializes and connects. Ordinary chat input does not initialize a deferred runtime. Cmd+Shift+C stays inactive until a real connected status arrives. The user chose this behavior over config mirroring or automatic reconnect-command injection.

`/pidewave`, registered by `acp.ts`, is the explicit user-invoked combination: it runs `ctx.reload()`, then `/mcp reconnect tidewave`. Reload replaces the extension runtime, so the old command handler opens a handoff in a dotfiles-owned `globalThis` slot; the reloaded runtime's `session_start` (reason `reload`) attaches a reconnect callback, and the old handler calls it once reload has fully returned. The callback sends `/mcp reconnect tidewave` through the new runtime's `sendUserMessage(..., { expandPromptTemplates: true })`, which dispatches the adapter command without a model turn. It first checks that `/mcp` is registered, because an unknown command would reach the model as chat. It skips reconnecting and warns when no runtime `tidewave` is registered (no `pidewave.url`, unsafe URL, or a configured duplicate). After the reconnect it confirms the result: the adapter publishes a status snapshot before its reconnect command returns, so ACP checks that the `tidewave` status is `connected` and that the runtime snapshot still belongs to its registration. It then notifies either `Pidewave: Tidewave connected at <origin>.` or why it did not connect (the adapter status, or an inactive or shadowed registration). If no status arrived during the command, it waits up to three seconds for one. A reload refused during streaming or compaction leaves no handoff, so a later plain `/reload` never reconnects. Neither command picks up a changed `PHX_PORT`; that still needs a Pi restart from the updated environment.

Automated checks cover endpoint validation, trust, interpolation, event order, revocation, frozen identity, duplicates, shutdown, fresh-factory reload, the `/pidewave` reload handoff and connection confirmation, bootstrap migration, CLI/footer behavior, and the existing Hammerspoon suites. `tests/pidewave-adapter.test.ts` runs separately against the real installed adapter with isolated config/cache: registration, deferred initialization, proxy-only namespace tools, snapshots, and disposal pass without network access. It does not prove a live Tidewave connection or Pi's complete reload flow. Scoped `hk` checks and `git diff --check` pass. The updater's separate regression suite is documented under [[lat.md/programs/pi-coding-agent#Runtime settings]].

Live rollout is still unverified and requires coordination: migrate the target project's config, reload Pi at a safe boundary, initialize/connect Tidewave if deferred, reload Hammerspoon only through `bin/hs-reload`, then test Cmd+Shift+C against an existing URL-matched Helium tab. Verify disconnected and unfocused Pis pass through, and no tab is opened, navigated, or launched.

### MCP reconnect error containment

MCP reconnect failures are contained so repeating server errors do not corrupt Pi's interactive TUI output.

`custom-footer.ts` patches `console.error` only for `MCP: Failed to reconnect to <server>:` messages, writes JSON lines to `~/.local/share/pi/logs/pi-mcp-adapter.log`, and suppresses the original console output. The footer exposes the captured failure through an internal `mcp-error` status rendered as red ` {server} {reason}` next to the compact ` n/N` MCP status. Reasons are short labels such as `conn refused`, `timeout`, `dns failed`, `auth failed`, `auth required`, `fetch failed`, and `sse error`. The red error is hidden once the parsed MCP status reports all configured servers connected.

Local Pi models use the `llamacpp` OpenAI-compatible provider at `http://127.0.0.1:18080/v1` with `llamacpp/qwen3.6`, `llamacpp/deepseek14b`, and `llamacpp/gemma4` aliases instead of Ollama or oMLX. Activation removes redundant `package.json`, `package-lock.json`, and `node_modules` from `~/.pi/agent/extensions` because Pi's own resolver handles deps.

Global MCP server config lives in `mcp.json`: `chrome-devtools-attach` connects to the running Helium debug port at `localhost:9223`; isolated `chrome-devtools` and copied-profile `chrome-devtools-profile` remain configured but disabled. Other global servers are remote `context7` with `CONTEXT7_API_KEY`, remote `githits` with bearer auth from `GITHITS_API_KEY`, command-backed `mise`, and stdio `sessions` (`sessions --mcp`, the nicknisi/sessions cross-tool session search/memory server). Local app-backed MCP servers such as Tidewave and Paper are not declared globally unless they are expected to be running, which avoids reconnect noise.

The `chrome-cdp` skill probes `CDP_PORT`, `CDP_PORT_FILE`, Helium's default port `9223`, then known browser `DevToolsActivePort` files. Each port is validated through `/json/version`, so stale port files do not block discovery.

Pi subagent orchestration comes from `git:github.com/amosblomqvist/pi-interactive-subagents`. It provides tmux-pane async subagents plus bundled `scout`, `researcher`, and `worker` definitions; the linked settings file contains no old `npm:pi-subagents` package-specific settings.

## Nvim review routing

Mise excludes `agent/extensions/_nvim-review.ts` from Pi's runtime, so `/piview` and its paired editor-service RPC route are inactive. Neovim-side review source remains for a future re-enable.

Scopes are `uncommitted`, `unpushed`, `branch`, `pr`, `ticket`, and `worktrees`. Diff modes are `status`, `worktree`, `staged`, `unstaged`, and `range`; they are forwarded as `{ scope, cwd, diff_mode }`.

It is distinct from `extensions/review.ts` (the `/review` pi-review-loop, which performs agent-driven checkout/snapshot reviews). `/piview` only targets the active paired Nvim and never scans manifests or steals pairs; when no editor service is connected (bare Pi) it spawns a review Nvim that pairs back (see [[lat.md/programs/neovim-pinvim#Pi-initiated review spawn]]). The Nvim-side handler is documented in [[lat.md/programs/neovim-pinvim#Worktree-aware PiReview]].

The former `pview` shell launcher now lives under `disabled/bin/` and is no longer linked into `~/.local/bin`.

## Preview command

The Pi `/preview` extension is a thin command parser around the `preview-ai` executable.

It accepts mode flags (`tmux-split`, `tmux-float`, `auto`), auto-close, delta, and HTML options, then forwards them to `preview-ai`. Tmux previews require a tmux session and render in a session-scoped pane or popup; HTML mode opens rendered markdown in a browser. Supported types are JSON, markdown, diff, codediff, log, file, image, command, text, and auto-detect. Task-tracker previews are intentionally unsupported.

`agent/extensions/view-image.ts` registers the `view_image` tool by reusing Pi's built-in read-tool parameters, execution, and result renderer. It is image-only guidance around the same attachment path, with a compact image-path call display; text files continue to use `read`.
